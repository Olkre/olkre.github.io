#Intro

AI is changing how design engineers turn designs into working interfaces. This article is a companion to AI in UX and Product Design. That one looks at research, visuals, and user flows. This one picks up where the design file ends: building components, wiring up tokens, adding motion, making screens accessible, and checking that the code actually matches the design. I build in React and SwiftUI (on iOS apps like SGym and FocusFence), so the examples lean that way, but the ideas apply to any stack.

#Where AI fits in design engineering

  • Handoff: reading a Figma frame and producing a first pass of component code.
  • Components and variants: turning a set of design variants into props, states, and a clean API.
  • Design tokens: extracting color, type, and spacing values and keeping them in sync between design and code.
  • Motion and interaction: translating a prototype's transitions into real animation code.
  • Accessibility: checking contrast, labels, focus order, and text scaling.
  • Responsive layout: adapting one design across phone, tablet, and desktop sizes.
  • Code review: comparing AI-generated UI against the design and catching missing states and edge cases.

#Design-to-code handoff

The concept: Handoff is the moment a design becomes something a developer can build. A good handoff is more than a screenshot. It includes spacing, sizes, states, behavior, and the reasoning behind decisions. As a design engineer, I'm often both sides of the handoff, so the goal is to lose as little detail as possible between the Figma file and the running app.

Where AI helps: AI can read a Figma frame (through a plugin, an MCP connection, or just a screenshot) and generate starter code for the layout. It can also write a short spec from the design: what each element is, what it does when tapped, and which values it uses. That gets me past the blank file quickly, so I can spend my time on structure and polish.

How it works

  1. Pick one screen or one component from the design file.
  2. Clean up the frame first: name layers, use auto layout, and apply styles instead of raw values.
  3. Give the frame to AI and ask for code in my stack (React with my styling setup, or SwiftUI).
  4. Ask it to list any values it guessed or couldn't read.
  5. Run the code, put it next to the design, and fix what doesn't match.

What to look for

  • Hard-coded values where a token or style already exists
  • One big component where the design clearly has smaller reusable pieces
  • Absolute positioning instead of a real layout (flex, grid, stacks)
  • Layer names copied into code as if they were meaningful names
  • Missing behavior the design implies but doesn't show (tap, hover, long press)

#Components and variants

The concept: A component is a reusable piece of UI, like a button, a card, or a list row. Variants are its different versions: sizes, styles (primary, secondary, destructive), and states (default, pressed, disabled, loading). In code, variants become props or modifiers. A good component has a small, predictable API that matches how the design system thinks about it.

Where AI helps: Give AI the full variant set from Figma and ask it to propose a props API before writing any code. It can spot which variants are really the same thing with one difference, suggest sensible defaults, and generate a preview or story that shows every variant side by side.

How it works

  1. Collect every variant of the component from the design file.
  2. Ask AI to map Figma variant properties to code props (or SwiftUI initializer parameters and modifiers).
  3. Review the API before any code is written. Rename and remove props that don't make sense.
  4. Have AI generate the component and a preview showing all variants and states.
  5. Compare the preview to the Figma variant grid.

What to look for

  • Props that overlap or contradict each other (for example two ways to set size)
  • States the design has but the code skips (disabled, loading, error)
  • Styling copied into each variant instead of shared
  • Names that differ between design and code for the same thing
  • Components that are too flexible to be useful

#Design tokens

The concept: Design tokens are the named values behind a design: colors, type sizes, font weights, spacing, corner radii, and shadows. Instead of writing #1A1A1A or 16 everywhere, code uses names like text-primary or space-4. Tokens make theming possible (light and dark mode, or brand variations) and keep design and code speaking the same language.

Where AI helps: AI can pull values out of a design file and organize them into a token structure, with base values (the raw palette) and semantic tokens (what each color is used for). It can convert tokens into the formats I need, like CSS variables for React and an asset catalog or Swift extension for iOS. It can also scan existing code for raw values that should be tokens.

How it works

  1. Export or list the color, type, and spacing styles from the design file.
  2. Ask AI to group them into base tokens and semantic tokens.
  3. Ask it to generate light and dark versions of the semantic tokens.
  4. Generate the code format for each platform.
  5. Ask AI to search the codebase for raw values and suggest which token should replace each one.

What to look for

  • Semantic names that describe a color instead of its purpose (blue-button instead of action-primary)
  • Near-duplicate values that should be one token
  • Dark mode colors that are just inverted instead of designed
  • A spacing scale with random gaps instead of a consistent step
  • Tokens that exist in design but not in code, or the other way around

#Motion and interaction

The concept: Motion shows what changed and where things went. Good interaction design covers transitions between screens, feedback when something is tapped, and small details like how a sheet settles or a toggle snaps. Motion should feel quick and purposeful, not decorative, and it should respect the user's reduced motion setting.

Where AI helps: AI can turn a description or a prototype recording into animation code, such as CSS transitions, Framer Motion in React, or SwiftUI animations and springs. It can suggest durations and easing curves, explain the tradeoffs between options, and add a reduced motion fallback I might forget.

How it works

  1. Record the prototype interaction from Figma or describe it step by step.
  2. Give AI the recording or description and ask for the animation in my stack.
  3. Ask it to explain each timing and easing value it chose.
  4. Run it on a real device and compare it to the prototype frame by frame.
  5. Tune the values by feel, then add the reduced motion version.

What to look for

  • Animations that are too slow or block the user from continuing
  • Motion that doesn't match the direction of the navigation
  • Animating layout properties that cause jank instead of transforms and opacity
  • No reduced motion fallback
  • Interactions with no feedback at all (taps that feel dead)

#Accessibility

The concept: Accessibility means everyone can use the interface, including people using screen readers, larger text, keyboards, or high contrast settings. In code it comes down to a few basics: enough color contrast, clear labels on every control, a logical focus order, tap targets that are big enough, and text that scales with Dynamic Type on iOS (or user font size on the web).

Where AI helps: AI can review component code and flag missing accessibility labels, images without descriptions, buttons that are only icons, and contrast ratios that fail. It can suggest labels and hints written in plain language, check that the focus order follows the visual order, and show how a layout should adapt when the text size gets very large.

How it works

  1. Pick one screen and give AI the code and a screenshot.
  2. Ask it to list every interactive element and its label, role, and focus position.
  3. Ask it to check text and icon colors against contrast guidelines using the actual token values.
  4. Test the screen with VoiceOver (or a web screen reader) and the largest text size.
  5. Fix the issues, then ask AI to review again.

What to look for

  • Icon buttons with no label, or labels like "button" or "image"
  • Text with fixed sizes that ignores Dynamic Type
  • Layouts that clip or overlap at large text sizes
  • Focus that jumps around or gets trapped
  • Color as the only signal for errors or status
  • Tap targets that are too small

#Responsive layout across devices

The concept: One design has to work on many screens: small and large phones, tablets, and desktop browsers, in portrait and landscape. Responsive layout is deciding what stretches, what wraps, what moves, and what hides as space changes. Designs usually show two or three sizes, so the code has to handle everything in between.

Where AI helps: AI can take a mobile and a desktop design and suggest how the layout should behave between them, including breakpoints, grid changes, and which elements reflow. It can write the layout code using flex, grid, or container queries in React, or adaptive stacks and size classes in SwiftUI, and point out where content might break.

How it works

  1. Collect every size the design shows for the screen.
  2. Ask AI to describe the layout rules that connect those sizes.
  3. Review the rules, then have AI write the layout code.
  4. Test the screen at the smallest, largest, and in-between sizes.
  5. Screenshot any breakage and give it back to AI to fix.

What to look for

  • Fixed widths or heights that break on other screens
  • Long text, long names, or translated strings that overflow
  • Content that is hidden on small screens with no other way to reach it
  • Breakpoints chosen by device instead of by when the content breaks
  • Safe areas and notches ignored on iOS

#Reviewing AI-generated UI code

The idea: AI-generated UI code often looks right in the happy path and falls apart everywhere else. Instead of trusting the first result, review it the same way I'd review a flow. Put the design next to the running build, go through every state, and record what happens. Then have AI help compare the two and list the gaps.

How it works

  1. Pick one component or screen that AI helped build.
  2. Record a video of it running, going through every state (empty, loading, filled, error, disabled).
  3. Take a screenshot of the design and the matching build for each state.
  4. Give the pairs to AI and ask it to list every visual and behavioral difference.
  5. Review the list against the visuals, fix what matters, and note what was intentional.

What to look for

  • Spacing, sizes, or colors that are close but not exact
  • States that exist in the design but not in the build, or the other way around
  • Edge cases like very long text, no data, slow network, and many items
  • Code that works but is hard to read or reuse
  • Accessibility and responsive issues from the sections above
  • Dependencies or patterns that don't fit the rest of the codebase

#Limits of AI in design engineering

  • AI can generate code that looks right but isn't structured well, so it still needs a real review.
  • It often guesses values it can't read from the design, and the guesses are easy to miss.
  • It doesn't know the rest of the codebase unless I give it that context, so it can repeat work or break patterns.
  • Motion and feel still need tuning on a real device. AI can't feel an animation.
  • Accessibility suggestions are a start, but testing with VoiceOver, large text, and real users is still required.
  • Generated code can include outdated APIs or made-up ones, so checking the docs matters.
